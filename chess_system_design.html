Overview

A real-time, stateful, multiplayer system. The whole design rests on one idea: the server is the single authority for each game — it validates every move, owns the clock, and is the source of truth both players render. Everything else (gateways, Redis, queues, Postgres) exists to make that fast, durable, and scalable.

The 5 signals that win it

1 · Server is authoritative

Validate every move server-side — legal? your turn? clock ok? That single rule is your anti-cheat and your consistency story.

2 · Split gateway from game logic

WebSocket gateways are memory-bound (idle connections); game servers are CPU-bound (validation). Scale each independently.

3 · Chess is event-sourced

The ordered move list IS the truth; the board (FEN) is a derived, replayable view. Makes history, replay, and crash-recovery trivial.

4 · DB off the hot path

Active game state lives in memory + Redis. Persist moves asynchronously. The database is for durability and history, not per-move latency.

5 · Don't over-engineer

Chess.com ran on one MySQL for years. Start simple; add Redis → sharding → multi-region as load demands. Judgment beats cargo-culting.

The move flow, step by step

Client A sends makeMove{gameId, move} over its WebSocket.
The WebSocket gateway routes it to the game server that owns this gameId.
The Game Service validates: active game? A's turn? legal move? clock not expired? — reject if not (anti-cheat).
Apply the move: update FEN, switch turn, deduct elapsed time + increment, write state to memory + Redis.
Append to the event log (source of truth); if the game ended, enqueue a rating-update event to Kafka.
Broadcast moveApplied{move, fen, clocks} to Player B (and any spectators) via pub/sub.
